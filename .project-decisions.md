# Project Decisions

> Durable current engineering decisions. Keep concise and current; this is not a changelog or task/session memory.

## Architecture
- Backends consume typed/resolved HIR, not raw AST; Eido semantic types remain independent of Nim representations.
- Core language operators stay deliberately small; derived math such as powers, roots, logarithms, and trigonometric functions belong in libraries.

## Language Semantics
- Supported primitives are Bool, Byte, Short, Int, Float, Char. Int is signed 64-bit; Float is 64-bit. Long/Double and numeric L/F/D suffixes are unsupported.
- Function inputs are 0..N parameters and function results are 0..1 values.
- Direct new-binding initialization from a bare existing identifier is rejected until explicit copy/ref semantics exist.
- Grouping delimiters `()`, `[]`, and `{}` are expression-equivalent matching pairs.
- Unary `-` is recursive and valid only for Int/Float.
- Equality requires matching primitive types; ordered comparison requires matching Byte/Short/Int/Float types. Integer literals may contextually adopt an opposite Byte/Short comparison operand.

- Expression precedence, highest to lowest: grouping -> unary `-` -> `* /` -> `+ -` -> `< <= > >=` -> `== !=` -> `not` -> `and` -> `or`.
- Boolean logic uses reserved word operators `not`, `and`, and `or`; symbolic `!`, `&&`, and `||` are unsupported as Boolean operators.
- Boolean operators accept only Bool and return Bool. `and` and `or` short-circuit.
- Conditional statements require `if (<Bool expression>) { ... }`, may contain zero or more `else if (<Bool expression>) { ... }` branches, and may end with optional `else { ... }`. Parentheses are mandatory around every `if`/`else if` condition for visual clarity.
- Conditional branches have isolated local scopes: outer bindings remain visible and assignable, branch-declared locals do not leak, and function-wide LocalIds remain unique across branches.
- A result function definitely returns when its final statement is `return` or a conditional chain whose every branch recursively definitely returns and whose chain ends with `else`; `if`/`else if` chains without a final `else` cannot alone satisfy the result contract.
- While loops use `while (<Bool expression>) { ... }`; parentheses are mandatory, the body has isolated local scope while retaining access/reassignment to outer bindings, and a while statement never by itself proves definite return.
- Classic for loops use `for (var <name> = <expr>; <Bool expression>; <assignment>) { ... }`. All three clauses and parentheses are mandatory in the first version. The initializer binding is scoped to condition/update/body, body locals do not leak to update, `continue;` executes the update before the next condition check, and a for loop never by itself proves definite return.
- Loop control uses semicolon-terminated `break;` and `continue;`. Both are legal only inside a loop and target the nearest enclosing loop; loop context is preserved through nested conditionals/blocks.
- Classes support nominal declarations using `class Name { Type field; }`. Field declarations use the existing semicolon terminator, while the closing brace ends the class with no trailing punctuation. Class names are collected before field resolution, so forward nominal field references are valid.
- Class construction is the expression `TypeName { fieldName: expression; ... }`. Every declared field is required exactly once; order is irrelevant; unknown/duplicate/missing fields and type mismatches are rejected; nested and zero-field construction are supported; construction fields do not implicitly enter one another's initializer scope.
- Class semantic types remain representation-neutral. The Nim backend currently uses generated `ref object` layouts only as an implementation detail. Class equality and bare class-to-class identifier reassignment remain rejected until explicit copy/reference semantics are designed; field access, mutation, and methods are still deferred.

## Code Organization
- Organize implementation and tests by semantic ownership, relevance, and locality; avoid growing generic hub files with feature-specific behavior.
- Keep small canonical vocabularies/data models centralized when they remain cohesive (for example token and AST/HIR expression enums); split behavior-owning logic instead of fragmenting a single source of truth.
- For expression behavior, stable hub modules coordinate shared dispatch while feature-specific parsing, analysis, and emission live in focused semantic subdirectories. `expression_parser.nim` stays thin: public entry point, precedence assembly, and genuinely shared helpers only. `expression_analysis.nim` likewise stays thin: public analysis APIs and expression-kind/operator dispatch only; concrete type rules belong under `semantic/analysis/expression/`. Internal `include` fragments are acceptable when they preserve one module's recursive/private parser or analyzer context without circular dependencies.
- Structured statement families follow the same model: `statement_parser.nim`, `statement_analysis.nim`, and `statement_emitter.nim` coordinate dispatch, while conditional/loop behavior lives under focused `statement/` modules. Share only genuine mechanics such as braced-block parsing and isolated scoped-block analysis.
- Tests mirror production semantic ownership; suites name the smallest useful semantic rule/family rather than catch-all categories or historical feature numbers. Language-facing expression tests live under `tests/features/expression/`, with a coverage index that explicitly records cross-catalog ownership and visible missing variant cases. Control-flow acceptance scenarios live under `tests/features/control_flow/`.

## Testing
- New language behavior follows explicit RED -> GREEN BDD per affected layer: write the owning Given/When/Then test, run and confirm meaningful failure, implement the minimum behavior, rerun to green, then refactor.
- User-visible behavior also receives a language-facing feature scenario, followed by the full `nimble test` conformance run.
- Feature acceptance executes generated Nim through `nim e` for speed; dedicated compiler pipeline tests retain real native-compilation coverage.
- `nimble test` compiles the complete aggregate once, then parallelizes execution with isolated processes. Compiler tests shard by suite; feature acceptance shards by individual test. Worker count defaults to `max(1, std/osproc.countProcessors() - 2)` to leave two logical cores free and can be overridden with `EIDO_TEST_JOBS`; the same count is used for Nim `--parallelBuild:N` during aggregate compilation.
