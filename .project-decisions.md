# Project Decisions

> Durable current engineering decisions. Keep concise and current; this is not a changelog or task/session memory.

## Architecture
- Backends consume typed/resolved HIR, not raw AST; Eido semantic types remain independent of Nim representations.
- Eido v0 remains one monorepo with sibling ownership areas for `compiler/`, `stdlib/`, `packages/`, `tools/`, `installer/`, integration tests, examples, and docs. A dedicated `runtime/` area is introduced only if Eido later owns hidden execution support required by language semantics.
- `stdlib/` is guaranteed with the installed SDK; `packages/` contains higher-level ordinary Eido libraries built on the language/stdlib and resolved as project dependencies rather than compiler extensions.
- Compiler semantic capabilities are exposed through a protocol-neutral tooling API. CLI, MCP, LSP, CI, and agent integrations adapt that API; compiler semantic code must not depend on MCP or a specific LLM/editor protocol. Tooling is developed in parallel with language semantics rather than deferred until language completion: when a feature creates new diagnostics, types, symbols, member behavior, formatting, navigation, or completion facts, the corresponding compiler query/tooling surface and LSP/editor behavior should be updated in the same development cycle where practical.
- Eido tooling should expose compiler-known semantic facts and diagnostics in structured form, support project/session and selective analysis over sound dependency cones, and provide compiler-grounded bounded context for agents. The compiler now owns a semantic symbol index that binds declaration/reference source spans to resolved class/interface/function/method/field/parameter/local identities; editor semantic tokens and go-to-definition consume that index rather than performing editor-side inference. MCP is a first-class planned adapter, conceptually launched through `eido mcp`, but Eido compilation remains deterministic and LLM-independent.
- Tooling and language now follow requirement-driven incremental development rather than independent parallel implementations: choose a permanent Eido ecosystem/tool capability, identify the missing prerequisite, classify it as language/stdlib/package/compiler-tooling/native support, implement it at the correct layer, then consume it immediately in the real Eido-written tool. Do not create throwaway dogfood applications merely to exercise syntax.
- The reference compiler/core remains Nim bootstrap infrastructure, but stdlib, packages, CLI, formatter, MCP, LSP, package tooling, and other ordinary ecosystem software should migrate to Eido whenever Eido can express them cleanly. Temporary Nim adapters are allowed only to unblock development and should remain thin enough to replace without losing semantic logic.
- The first permanent Eido-written product is the CLI under `tools/cli/eido/`. It currently implements `help`, `version`, unknown-command diagnostics, and process exit behavior. The existing Nim CLI under `tools/cli/src/` remains the bootstrap front door for `build`/`check` until the Eido implementation gains the capabilities required to take them over.
- The compiler project model is now first-class: one `EidoProject` contains explicit `SourceUnit` values and a `ProjectTarget` (`ptExecutable` or `ptLibrary`). Source units carry project-local identity, physical/logical path, and text; source spans retain source identity/path through lexer, parser, semantic analysis, and diagnostics.
- Compiler diagnostics are structured compiler-owned data: stable code, severity, human message, and optional source span. `CompilerError` remains `ValueError`-compatible for existing compiler internals while embedding the structured diagnostic. Tooling uses `ProjectCheckResult` instead of parsing exception strings. Current stable codes begin with generic source error `EIDO1000`, empty project `EIDO2001`, and missing executable `main` `EIDO2002`; more specific codes are introduced incrementally as language areas evolve rather than by a risky mass rewrite.
- `checkProject` is a semantic/tooling operation: it runs project parsing + semantic analysis only, returns success/diagnostics/analyzed HIR, catches expected `CompilerError`s, and deliberately lets unexpected compiler/backend invariant failures propagate. The current compiler remains fail-fast, so a check presently returns at most one diagnostic even though the result model supports multiple diagnostics for future recovery/aggregation.
- `native function` is the explicit host/backend boundary required to build stdlib/tooling in Eido. It is bodyless, semicolon-terminated, and uses ordinary typed parameters/results. Native declarations may be top-level or class-owned. A class-owned native function is necessarily type-associated/static in v0 (there is no Eido body from which to derive a receiver) and is called directly as `Type.method(...)`; native instance methods are not supported. The initial ABI permits only primitives and String; class values are rejected until class/native identity, representation, lifetime, and mutation semantics are deliberately designed. `main` cannot be native. This remains an SDK/backend support ABI, not yet a general arbitrary-library FFI design.
- Foundational stdlib APIs should not add an Eido wrapper merely to rename a native capability. When the public operation is itself the native boundary, declare it directly on the API class, e.g. `class Console { native function writeLine(String value); }` and `class Process { native function argument(Int index) returns String; }`. The Nim backend maps class-owned native calls to class-scoped ABI symbols (`eido_native_method_<Owner>_<method>`), while top-level native functions retain their existing `eido_native_<name>` mapping.
- Core language operators stay deliberately small; derived math such as powers, roots, logarithms, and trigonometric functions belong in libraries.
- The v0 syntax/core surface is frozen after managed class-owned bootstrap state. Further language syntax or semantics are added only when real Eido application dogfooding demonstrates that the existing core cannot express a requirement cleanly; missing application capability should default to stdlib/package/runtime/tooling work instead.
- `examples/eido-memory-management` is the canonical post-freeze memory dogfood example: ordinary Eido owns heap policy and process state above public `Storage<T>`, with a uniquely named internal `heap_runtime` module whose managed `HeapState` is held by class-owned state as a permanent root and a static `MemoryManager` facade as the module API; example child-module names should avoid collisions with implicit SDK modules such as `eido.stdlib.memory`.

- The official `eido` executable is the default project/build tool, not a mandatory build system. Normal project commands (`check`, `build`, `run`, `clean`) may discover the outermost ancestor `module.yaml` and use `<project>/build/` defaults, while explicit manifests/output paths and standalone `eido compile` remain available. Compiler/project semantics stay below the CLI so future Maven/Gradle/Bazel-style tools can provide independent orchestration, lifecycle, caching, profiles, artifact layout, and dependency management without changing the language or compiler model.

- Normal `module.yaml` projects receive an implicit exported SDK dependency `eido.stdlib`. Its architecture is declared by the real stdlib manifest tree: the root manifest owns umbrella children/re-exports while each child manifest owns its sources and local exports. The bootstrap compiler embeds and recursively parses those same manifests and source payloads instead of maintaining handwritten flattened stdlib metadata. User manifests must not reference compiler-repository stdlib paths. `EIDO_NATIVE_NIM_PATH` remains an explicit backend-support override. The low-level standalone `eido compile` route does not define the full project/SDK environment.
- The SDK stdlib itself is a real module tree rather than one flattened module: source-free `eido.stdlib` is the umbrella; `eido.stdlib.process` and `eido.stdlib.io` own ordinary public capabilities, while `eido.stdlib.memory` is a source-free namespace for standard memory-policy implementations. `eido.stdlib.memory.managed` owns the default hidden memory-policy runtime code; `eido.stdlib.text` owns built-in String runtime code; `eido.stdlib.runtime` owns other hidden language-runtime services such as detached-copy memoization. Hidden language-runtime sources use generic `soLanguageRuntime` origin plus a compiler-known language capability (`lrcString`, `lrcClassCopy`) so target compilation injects only the facilities actually required by user HIR, independently of GC policy. The umbrella re-exports only ordinary public child API roots; manifests, docs, dependencies, and internal runtime ownership remain component-local.

## Language Semantics
- Supported primitives are Bool, Byte, Short, Int, Float, Char. Int is signed 64-bit; Float is 64-bit. Long/Double and numeric L/F/D suffixes are unsupported.
- String is a separate built-in immutable text value, not a primitive and not a class. String has no observable object identity; `copy`/`ref` are invalid for String. Target String values use an opaque machine-word handle whose immutable UTF-8 byte backing is owned by hidden ordinary Eido language-runtime code over `Storage<Byte>`. The current runtime keeps String allocations for program lifetime and releases them at shutdown. Native/platform String values are foreign temporaries only: generated ABI bridges copy native text into Eido String storage on return and materialize a temporary native string only when passing Eido text outward.
- Function inputs are 0..N parameters and function results are 0..1 values. Parameters/results may use primitive, String, or declared nominal class types.
- Existing class identity never silently establishes or replaces a persistent class relationship. New local bindings, class construction fields, class-local `set`, and own class-field `set` require explicit `ref` to preserve identity or `copy` to detach when the source is an existing class object. `copy`/`ref` are not parameter, return, or callable-result modifiers.
- Source mutation uses reserved `set`: `=` establishes an initial value, while `set <name> = <expr>;` mutates a local, `set self.<field> = <expr>;` mutates instance state, and `set Type.<field> = <expr>;` mutates class-owned state. Bare reassignment is invalid. Parameters and external instance fields are not mutation targets. String storage locations may be replaced with new String values, but String contents are immutable. For class-valued instance targets, fresh construction and detached callable results flow directly, while existing class objects require explicit `ref` or `copy`.
- Grouping delimiters `()`, `[]`, and `{}` are expression-equivalent matching pairs.
- Source comments use `//` and continue through newline or end-of-file. Comments are lexer trivia and never enter the parser/AST; `//` inside String literals remains ordinary String content, while a single `/` remains division. A contiguous `///` block immediately above a declaration is tooling-owned API documentation metadata; ordinary `//` remains an implementation comment, and a blank/ordinary-comment gap breaks attachment. Documentation comments do not change language semantics. Block comments are not part of the current v0 surface.
- Unary `-` is recursive and valid only for Int/Float.
- Equality requires matching primitive types or matching String operands; String equality is content equality. Ordered comparison requires matching Byte/Short/Int/Float types. Integer literals may contextually adopt an opposite Byte/Short comparison operand. String supports `+` concatenation and no other arithmetic operator.

- Expression precedence, highest to lowest: primary/grouping/construction -> postfix field access -> unary `-` -> `* /` -> `+ -` -> `< <= > >=` -> `== !=` -> `not` -> `and` -> `or`.
- Boolean logic uses reserved word operators `not`, `and`, and `or`; symbolic `!`, `&&`, and `||` are unsupported as Boolean operators.
- Boolean operators accept only Bool and return Bool. `and` and `or` short-circuit.
- Conditional statements require `if (<Bool expression>) { ... }`, may contain zero or more `else if (<Bool expression>) { ... }` branches, and may end with optional `else { ... }`. Parentheses are mandatory around every `if`/`else if` condition for visual clarity.
- Optional values use `T?` with absence written as `none`. Ordinary `T` is definitely present. Source never unwraps through `.value`/`.get`/`.unwrap`; the only access gate is the lexical `if <stable-path> exists { ... }` block, which proves that exact path as `T` only inside its body. Proofs nest, do not escape, and are intentionally not invalidated by mutation/aliases/calls in the initial model; even direct `set X = none` does not yet invalidate the active proof. A future local semantic refinement may reject later use after an obvious direct `none` assignment without introducing alias/effect analysis.
- Conditional branches have isolated local scopes: outer bindings remain visible and mutable through `set`, branch-declared locals do not leak, and function-wide LocalIds remain unique across branches.
- A result function definitely returns when its final statement is `return` or a conditional chain whose every branch recursively definitely returns and whose chain ends with `else`; `if`/`else if` chains without a final `else` cannot alone satisfy the result contract.
- While loops use `while (<Bool expression>) { ... }`; parentheses are mandatory, the body has isolated local scope while retaining access and `set` mutation of outer mutable bindings, and a while statement never by itself proves definite return.
- Classic for loops use `for (var <name> = <expr>; <Bool expression>; set <name> = <expr>) { ... }`. All three clauses and parentheses are mandatory in the first version. The initializer binding is scoped to condition/update/body, body locals do not leak to update, `continue;` executes the `set` update before the next condition check, and a for loop never by itself proves definite return.
- Loop control uses semicolon-terminated `break;` and `continue;`. Both are legal only inside a loop and target the nearest enclosing loop; loop context is preserved through nested conditionals/blocks.
- Classes support nominal declarations using one construct. `Type field;` declares ordinary per-instance state. `Type ClassName.field = expression;` explicitly declares one class-owned mutable slot; it is accessed/mutated only as `ClassName.field`, while instance state is accessed through a value/`self`. The qualifier must name the containing class, so no `static` keyword or singleton construct is required. Class-owned fields are separate from instance payloads, constructors, copying, tracing, and instance layout. Backend lowering keeps the class-owned slot itself as inline process-lifetime representation; it does not dynamically allocate storage merely to hold the slot. Dynamic backing referenced by the slot remains owned by Storage/language runtime/selected memory policy. Under managed GC, class/interface-valued class-owned slots are permanent precise roots: every root registry-entry handle is declared first, all managed slots are registered before any class-owned initializer runs, and reassignment updates the existing registry entry rather than replacing its identity. Existing class identities still require explicit `ref`/`copy`; process-lifetime roots are never popped.
- Generic classes use `class Name<T, ...>` and explicit applications such as `Name<Int>`; arity is N, arbitrary nested applications are legal, raw generic uses and inference are not. The compiler statically specializes used generic applications into ordinary concrete nominal classes before semantic analysis, so existing copy/ref, mutation, method, and detached-return rules apply after substitution without generic exceptions. Generic functions/method-local type parameters, constraints, variance, wildcards, generic interfaces, and generic native class methods remain deferred.
- Class construction is the expression `TypeName { fieldName = expression; ... }`. It initializes instance fields only; class-owned fields have their declaration initializer and never appear in object construction. Every instance field is required exactly once; order is irrelevant; unknown/duplicate/missing fields and type mismatches are rejected. An existing class value used for a class-valued instance field requires `ref` or `copy`; fresh construction and detached callable results may flow in directly.
- Class field access uses postfix `receiver.field` and may chain left-to-right. The receiver must have a nominal class type and the field must exist on that class; the expression type is the field's declared type. Postfix access is observational: external `set receiver.field = ...` is invalid.
- Class-owned functions use one `function` syntax with no `static` keyword. The compiler infers method kind from explicit `self` dependency: any reachable `self` use makes it an instance method; a self-free body is type-associated. Class-owned state is explicit instead through qualified field declarations (`Type ClassName.field = ...`) and `ClassName.field` access, so method and state ownership remain readable without a `static` keyword.
- Inferred static methods provide Java-like type/utility grouping without a `static` keyword or a separate namespace construct: e.g. `Console.writeLine(...)`, `Process.argument(...)`, `Money.fromCents(...)`. Modules remain architectural source/dependency boundaries and are not replaced by this class-level grouping.
- Method effective namespaces forbid: field↔parameter collisions, field↔local collisions, parameter↔local collisions, and local↔nested-local shadowing. Names may be reused independently in different methods. Method names are unique within one class; method overloading is unsupported in v0.
- Class methods may mutate their own fields only through `set self.field = ...`. Non-class fields accept type-compatible values; class-valued fields accept fresh/detached values directly or existing objects through explicit `ref`/`copy`. This mutation authority is class-owned; parameters and external postfix fields are not mutation targets. The existing field↔parameter/local and local-shadowing restrictions remain even though `self` makes receiver access syntactically explicit.
- Class parameters preserve the caller's logical object identity for the call; callers can invoke behavior on that object, while direct field mutation remains class-owned through `set self.field = ...`. Class-valued returns must be fresh/detached: returning a parameter, `self`, an existing class field, or a ref-bound local is rejected; fresh construction, detached callable results, and detached locals are valid.
- `copy` recursively detaches the reachable class graph and preserves internal sharing/cycles within the copied graph; `ref` preserves the same logical object identity. These are source-level identity semantics, not a memory-management commitment. Compiler-generated copy traversal owns graph semantics only; memo ownership is supplied by hidden Eido `CopyRuntime`, which stores heterogeneous source→target identity pairs in a growable raw Storage block and explicitly releases that scratch backing after each successful public copy operation.
- Class semantic types remain representation-neutral. The Nim backend currently uses generated `ref object` layouts, memoized graph copiers, and hidden receiver parameters only as implementation details. Class equality remains unsupported.
- Normal Eido projects are module-driven through a mandatory separate YAML manifest named `module.yaml`; module vocabulary never becomes reserved `.eido` syntax. The manifest explicitly owns source files, child modules, direct dependencies, exports, child providers, and adopted child contracts. Filesystem nesting alone has no architectural meaning and undeclared source files are not compiled.
- Module containment is asymmetric: only a parent declares its children; children do not declare or depend back on their parent. Parent-authorized architecture propagates downward (including ancestor dependencies and parent/family contracts), while nothing from a child propagates upward automatically. A child export reaches the parent/siblings only through explicit parent `adopts` or public re-export. Parent/child containment and module dependency edges are distinct.
- Explicit module dependencies are non-transitive usage relationships and must form a DAG. A parent owns the architecture of its module family. Explicit export roots are restricted to interfaces and static-only classes; a static-only export class has zero fields and only inferred/static-native methods. Top-level functions and concrete instance classes cannot be explicit export roots. From each legal root, the compiler computes a transitive nominal API closure through class fields, class method parameter/results, implemented interfaces, interface parents, interface method parameter/results, and nested generic arguments. Ordinary stateful/behavioral classes may therefore become reachable transitively when required by an exported contract or static facade, and then remain available as their complete current language surface; unreachable declarations remain module-internal. If A's public API intentionally reaches a declaration exposed by dependency B, that specific reachable declaration is re-exposed without making B's unrelated declarations transitively visible. There is no DTO/data-class distinction for transitively reachable classes.
- Interfaces are explicit nominal architectural contracts: `interface Name { function ...; }`, classes declare `implements A, B`, and an interface may `extends` one parent interface in v0. Class conformance requires exact instance-method signatures; self-free/static methods do not satisfy interface contracts. Generic interfaces and multiple-interface extension are deferred.
- Interface methods may carry bodyless `require`/`ensure` contracts. Their scope is parameters, contextual `result` in value-returning `ensure`, and `self` through interface-visible methods. Interface contracts propagate into concrete implementations and remain separate from implementation-declared contracts; both are enforced at the concrete method boundary, including direct concrete calls. Child interface redeclarations must preserve the inherited signature and add behavioral obligations rather than replacing parent contracts. A class may not implement two independently declared interface methods with the same method name; the same original declaration inherited through multiple paths is allowed. Static compatibility/proof rules between inherited and implementation clauses are intentionally a separate verification feature.
- Interface values are real runtime-dispatch values. A class value converts to an interface only through explicit `implements`; a child-interface value converts to an ancestor only through `extends`. HIR distinguishes interface dispatch from direct class dispatch. Interface values preserve the hidden implementation identity but are opaque behavioral handles; source `copy`/`ref` remain concrete-class operations.
- Module-owned declaration identity is canonicalized as `<canonical-module>.<local-name>` before ordinary semantic analysis (for example `shop.payments.Result`). Different modules may therefore declare the same class, interface, or module-internal top-level function name without collision. Source code remains concise: an unqualified nominal resolves to the same-module declaration first, otherwise to the single visible declaration reachable through the effective exported/adopted/provided/dependency API surfaces. If multiple visible declarations share the name, the reference is rejected as ambiguous and source code must disambiguate with a module-qualified name such as `payments.Result`. Qualification is supported in declared types, construction (`payments.Result { ... }`), and class/static access (`payments.Factory.create()`); it never bypasses visibility/dependency rules. Top-level functions remain module-internal and are internally canonicalized, but there is no cross-module function-call qualification.
- Module-owned interfaces are closed to their owning module family by default. Interfaces in module projects must participate in some exported, adopted, or provided API surface, either directly or by transitive nominal reachability. `provides: Contract: by: child` verifies that the contract is a parent-owned interface and that the declared provider subtree contains an implementation. Open/plugin implementations require a future explicit opt-in rather than being allowed implicitly.
- Executable projects require exactly one top-level function named `main`; ordinary duplicate-function rules reject multiple mains, and executable `main` must have zero parameters. Library projects do not require an entrypoint and emit no executable main harness. The current backend still prints a value-returning main as a temporary testing/development harness; final process-exit/output semantics remain to be defined when stdlib/process behavior is implemented.

## Code Organization
- Organize implementation and tests by semantic ownership, relevance, and locality; avoid growing generic hub files with feature-specific behavior.
- Keep small canonical vocabularies/data models centralized when they remain cohesive (for example token and AST/HIR expression enums); split behavior-owning logic instead of fragmenting a single source of truth.
- For expression behavior, stable hub modules coordinate shared dispatch while feature-specific parsing, analysis, and emission live in focused semantic subdirectories. `expression_parser.nim` stays thin: public entry point, precedence assembly, and genuinely shared helpers only. `expression_analysis.nim` likewise stays thin: public analysis APIs and expression-kind/operator dispatch only; concrete type rules belong under `semantic/analysis/expression/`. Internal `include` fragments are acceptable when they preserve one module's recursive/private parser or analyzer context without circular dependencies.
- Structured statement families follow the same model: `statement_parser.nim`, `statement_analysis.nim`, and `statement_emitter.nim` coordinate dispatch, while conditional/loop behavior lives under focused `statement/` modules. Share only genuine mechanics such as braced-block parsing and isolated scoped-block analysis.
- Project ownership is split deliberately: `source/` owns source identity/spans, `project/` owns target/source-set data, `frontend/parser/project_parser.nim` assembles per-source ASTs, `pipeline/project_compiler.nim` orchestrates project analysis/emission, and `tooling/compiler_service.nim` exposes protocol-neutral check/compile operations to CLI/LSP/MCP adapters. Generated API documentation is also protocol-neutral compiler tooling: `documentation_service.nim` reuses module public-surface closure and source spans, `documentation_rendering.nim` emits HTML/JSON, and the CLI only owns filesystem/output orchestration through `eido doc`. Compiler-provided public surfaces such as `Storage<T>` must be labeled separately rather than omitted or confused with source declarations; backend implementation symbols are not Eido API.
- Native platform implementation belongs outside compiler semantics: Eido declarations live in capability-owned stdlib modules (`stdlib/process/`, `stdlib/io/`, `stdlib/memory/`), the Nim-backend provider lives in `stdlib/native/nim/eido_native.nim`, and backend toolchain code only resolves/imports that support module. `Process` and `Console` now expose their native operations directly as class-owned native methods, so no separate Eido `platform*` wrapper layer exists in shipped stdlib source. Process arguments, stdout/stderr, and process exit remain the first platform capabilities because they are directly required by the permanent Eido CLI.
- Tests mirror production semantic ownership; compiler-internal and language-facing conformance tests live under `compiler/tests/`, while root `tests/integration/` is reserved for cross-component SDK/tool/library integration. Structured diagnostic behavior lives under `compiler/tests/diagnostics/`; project behavior under `compiler/tests/project/`. Language-facing expression tests live under `compiler/tests/features/expression/`, with a coverage index that explicitly records cross-catalog ownership and visible missing variant cases. Control-flow acceptance scenarios live under `compiler/tests/features/control_flow/`.

## Testing
- New language behavior follows explicit RED -> GREEN BDD per affected layer: write the owning Given/When/Then test, run and confirm meaningful failure, implement the minimum behavior, rerun to green, then refactor.
- User-visible behavior also receives a language-facing feature scenario, followed by the full `nimble test` conformance run.
- Feature acceptance executes generated Nim through `nim e` for speed; dedicated compiler pipeline tests retain real native-compilation coverage.
- `nimble test` compiles the complete compiler/language aggregate once, then parallelizes execution with isolated processes. Compiler tests shard by suite; feature acceptance shards by individual test. Worker count defaults to `max(1, std/osproc.countProcessors() - 2)` to leave two logical cores free and can be overridden with `EIDO_TEST_JOBS`; the same count is used for Nim `--parallelBuild:N` during aggregate compilation. Root `tests/integration/` then runs cross-component toolchain tests, including the bootstrap CLI and a permanent dogfood test that compiles/runs the Eido-written CLI itself.

- Design by Contract v0 uses optional `require`, `ensure`, and `invariant` sections with unnamed non-empty Bool clauses. `require` precedes executable callable statements, `ensure` is the final callable section, and classes may declare at most one invariant section. Contracts are first-class AST/HIR facts and lower to always-enabled runtime checks; class invariants are checked after construction and instance-method execution. `old`, named clauses, `modifies`, and purity syntax are not part of this v0 slice.
- Contract expressions are observational without a source-level `pure` keyword. The compiler infers contract safety transitively from resolved HIR: own-field mutation is an observable effect; local-variable mutation is not; concrete Eido calls inherit unsafety through the call graph. Native calls and dynamic interface dispatch are conservatively contract-unsafe unless the compiler explicitly verifies a native operation as observational; current Storage exceptions are `capacity`, `size`, and `alignment`. These restrictions apply only inside `require`, `ensure`, and `invariant`; ordinary code remains unrestricted.
- Runtime contract boundaries are explicit rather than Nim-`defer`-based. `ensure` executes only on normal exits after the return expression is evaluated, so abnormal runtime failures preserve their original cause. A class invariant is checked after construction, on every instance-method entry and normal exit including nested same-object calls, and immediately after each `set self.field = ...`; temporary invariant violations are therefore forbidden. A backend-only per-object invariant-evaluation guard suppresses recursion only while the invariant itself is evaluating, allowing observational helper methods without weakening ordinary nested-call checks.
- `result` is a contextual postcondition binding, not a globally reserved keyword. Parameters/locals may use the name `result` normally outside `ensure`. Inside `ensure` of a value-returning callable, contextual `result` shadows any ordinary binding with that name, has exactly the declared result type, and denotes the value selected by every successful return path. Inside `ensure` of a zero-result callable, `result` is invalid even if an outer binding exists. The backend evaluates each return expression once, binds that value to the HIR result local, checks `ensure`, then returns the same value. `ensure` constrains the whole observable post-state, including side effects such as mutated `self`/parameter-reachable state; contract evaluation itself remains observational.

## Storage substrate
- Eido has one low-level memory family: `Storage<T>`. `Storage<Byte>` is the universal raw backing representation for heterogeneous regions; typed storage, future object layouts, strings, arenas, pools, pages, arrays, vectors, and maps build above the same substrate rather than introducing parallel object/collection allocators.
- Allocation creates capacity rather than source-level values. `Storage<Byte>.allocateRaw(allocations, bytesPerAllocation)` is the single physical owned-allocation path. `Storage<T>.allocate(allocations)` derives the target slot width from `T`, acquires its backing through that raw path, then adopts the same bytes as an owning typed descriptor. `Storage<Byte>.fromAddress(startingAddress, allocations, bytesPerAllocation)` describes the same block model at an explicit base address. `Storage<T>.view(raw, start)` is the explicit borrowed raw-to-typed boundary and `slice` derives allocation-free borrowed subranges. `read`/`write` remain purely typed APIs; `Storage<T>.size()` and `alignment()` are the sole public target-layout queries.
- Storage ownership is compiler/runtime semantics: `allocate`/`allocateRaw` create owning roots, `fromAddress` creates a non-owning external root, `adoptAddress` explicitly reconstructs ownership of an existing raw allocation, and `view`/`viewAt`/`slice` results are borrowed. `address` exposes a live Storage base address; `viewAt` creates a typed one-slot view at a checked byte offset inside a raw block. These low-level operations let Eido runtimes describe metadata directly in Storage without a parallel native representation.
- The hosted Nim backend implements only the physical Storage mechanics in `stdlib/native/nim/eido_storage.nim`; generated code contains concrete aliases/thin glue. `EidoStorage[T]` is an allocation-free descriptor carrying base pointer, slot capacity, stride, ownership/release state, raw/typed state, and liveness. Primitive raw-to-typed Storage and pure String allocation/concatenation/equality compile and run under Nim `--mm:none`; detached graph-copy scratch is also Eido/Storage-owned rather than a Nim container. Remaining every-path memory-manager-independence work is centered on trap/exception handling and other explicitly documented backend dependencies.
- Memory-management policy above Storage belongs in Eido. Standard and custom policies implement their own allocation/lifetime algorithms directly over `Storage<T>` and the compiler-facing memory-policy API; the stdlib does not impose an intermediate generic `Memory<T>`/allocator facade.
- Borrowed Storage values may be returned from ordinary Eido callables when result provenance is statically inferable; callers preserve borrowed/non-releasable status, while fresh Storage roots still transfer ownership. Full lifetime invalidation across arbitrary owner mutation/release remains future control-flow/borrow-analysis work.
- `Storage.capacity`, `Storage<T>.size()`, and `Storage<T>.alignment()` are compiler-owned Storage operations treated as verified observational behavior inside contracts. Allocation, write, release, and other native operations remain effectful or conservatively unverified.
- `eido.stdlib.memory` intentionally exports no ordinary application memory facade. It is a namespace for standard policy implementations such as `eido.stdlib.memory.managed`; application/runtime authors use `Storage<T>` directly and policy authors use the compiler-facing memory-policy API.

## Compiler-standard Eido compile-time phases
- Compiler work that is naturally expressible in Eido may run on the build machine during compilation. Memory metadata is the first substantial use of that mechanism.
- Build-machine memory-policy modules use a supported compiler-facing Eido API (`Compiler`, `TypeInfo`, `FieldInfo`, `CallableInfo`, `ValueInfo`, `StorageInfo`, `MemoryPolicy`) that ordinary application source cannot name. It exposes semantic facts and neutral lifecycle-event binding only; it is not general reflection or FFI. Compiler-internal metadata records such as `MemoryMetadata`/`MemoryMetadataBuilder` remain private implementation contracts.
- Memory policy selection is module-based. `CompilationOptions.memoryPolicy` carries a selected module identity or no policy. The CLI alias `gc` selects `eido.stdlib.memory.managed` by default; `none` and compatibility alias `manual` select no automatic policy; any other `--memory=<module>` value selects that loaded policy module. The compiler contains no GC/manual strategy enum. Nim backend memory-manager options remain separate.
- **Compiler memory output is policy-neutral metadata.** The compiler/Eido metadata phase describes target size/alignment, field offsets, identity-bearing fields, and identity-valued parameters/locals/receivers/results. Separately, the compiler exposes generic semantic event points such as binding enter/write/leave, construction storage acquisition, temporary-expression scope, statement boundary, invariants, and program exit. It must not assign GC/RC/arena meaning to those events or select roots, tracing, safepoints, marking/sweeping, retain/release actions, arena ownership, collection thresholds, or allocator policy.
- The compiler answers **what exists**; Eido memory code decides **how it lives**. This applies to every future policy (GC, arena/region, reference counting, pools, manual/embedded allocation, hybrids) rather than adding a compiler branch for each strategy.
- **Construction and allocation are separate.** `Class { ... }` remains a compiler-owned language-semantic construction operation: resolve the type, validate/initialize fields, preserve identity/ref/copy semantics, and enforce contracts/invariants. Obtaining physical backing for a runtime-backed identity is an Eido memory-policy operation. The compiler exposes a generic construction-storage event; the selected Eido compile-time memory policy chooses its ordinary Eido handler. The compiler never selects a GC/arena/RC allocator.
- The compiler-internal `memory_metadata` Eido phase computes generic layouts and identity facts. Its output uses temporary build-invocation handles that the compiler resolves back to stable semantic identities before backend generation; no collector plan crosses that boundary. A selected policy receives the same read-only semantic snapshot APIs when its `policySources` execute.
- Dynamic target layout remains grounded in Storage semantics. The private phase bridge can query target size/alignment for compiler-known types while ordinary Eido continues to see only `Storage<T>.size()` / `Storage<T>.alignment()`.
- Compile-time phase/policy executables are cached build-machine artifacts. Their compiler-facing APIs, native bridge, and semantic snapshot never enter target binaries; a policy module’s ordinary `sources` are separately injected as its target runtime only when selected.
- **Storage is the universal dynamic target-memory substrate.** Owned dynamic backing regions—object payloads, strings, registries, heaps/regions/pools, collector state, arrays/containers, and future policy allocations—must be realizable above `Storage`. Inline/register/stack/static representation slots and Storage descriptors are not independent dynamic owners. The compiler may describe structure/lifetimes and emit inline representation, but it must not initiate a competing dynamic allocation path; actual object addresses come from the selected Eido policy.
- Any module declaring `policySources` is a memory-policy module. Its ordinary target `sources` carry generic `soMemoryPolicyRuntime` origin; base analysis filters them, and target compilation injects only the runtime sources of the selected policy module. The same mechanism applies to the SDK GC and user policy modules. Compiler semantics must not identify policy filenames or implementation classes.
- A selected Eido policy binds only the generic semantic event points it needs through the public `MemoryPolicy` compile-time API. Handler references are class-qualified ordinary static Eido methods and are checked against stable typed event contracts. Type/field metadata remains generic data; `objectAcquire(payloadSize, payloadAlignment, typeId) -> Int` is the current construction/storage boundary; the policy returns the actual target identity/address. The compiler never allocates that address and never emits or names `root`, `trace`, `safepoint`, `collect`, `retain`, or similar policy actions.
- The default `gc` implementation is an ordinary selectable SDK policy module under `stdlib/memory/managed/`. Its `policy.eido` uses the same `MemoryPolicy` API available to user modules, while `MemoryValueRegistry`, `MemoryTypeRegistry`, `ManagedGcRuntime`, `ManagedHeapAllocator`, and `MemoryRuntime` are merely that policy’s target implementation. The standard GC has no privileged compiler path.
- The Nim backend has no dedicated managed-GC native support module. Runtime-backed class/interface identities currently lower to `Int`-sized backend handles (`int64` in Nim); generated Nim performs only representation glue such as presence checks and typed payload-address casts. Memory ownership and policy remain Eido code above `Storage`.
