# Project Map

> Navigation cache. Source files are authoritative.

## Project
Eido is a Nim-written native compiler for a Java-like language. The compiler now operates on explicit multi-source projects, lowers typed/resolved HIR to generated Nim/native code, and exposes protocol-neutral tooling services for CLI/LSP/MCP growth.

## Areas
- `compiler/src/source/` — source identity/text/span model; start: `source_unit.nim`, `span.nim`
- `compiler/src/project/` — compiler-level project/target model; start: `model.nim`
- `compiler/src/frontend/` — per-source lexing/AST/parsing plus project AST assembly; start: `scanner.nim`, `expression_parser.nim`, `project_parser.nim`
- `compiler/src/semantic/` — name resolution/type analysis; start: `program_analysis.nim`, `expression_analysis.nim`
- `compiler/src/types/` — language semantic types/contracts; start: `model.nim`
- `compiler/src/hir/` — typed/resolved backend-facing representation; start: `expressions.nim`, `program.nim`
- `compiler/src/backend/nim/` — HIR→Nim emission and native toolchain; start: `program_emitter.nim`
- `compiler/src/tooling/` — protocol-neutral project check/compile/editor-query/documentation services for CLI/MCP/LSP/CI; `checkProject` returns structured diagnostics + analyzed HIR, `hover_service.nim` derives semantic hover, `formatting_service.nim` owns canonical formatting, `comment_service.nim` exposes lexer-grounded comments plus attached `///` docs, `documentation_model.nim` / `documentation_service.nim` / `documentation_rendering.nim` own generated API reference facts + HTML/JSON, and `symbol_service.nim` + `tooling/symbols/` own semantic declaration/reference identity for highlighting/navigation
- `compiler/tests/` — compiler-internal and language-facing conformance tests; aggregate: `compiler_test_suite.nim`; runner: `parallel_test_runner.nim`
- `tools/cli/src/` — temporary Nim bootstrap `eido` adapter used until Eido CLI parity
- `tools/cli/eido/` — permanent CLI implementation written in Eido; currently help/version/unknown-command behavior
- `tools/mcp/` — planned MCP protocol adapter over compiler tooling; no MCP behavior implemented yet
- `tools/lsp/src/` — working editor-neutral stdio LSP adapter: JSON-RPC lifecycle, full document overlays, project-aware live diagnostics, semantic hover, semantic tokens, go-to-definition, and document formatting; compiler semantics remain in protocol-neutral tooling
- `tools/vscode/` — thin VS Code/Cursor client for `eido-lsp`, .eido language registration/TextMate + semantic coloring, hover/definition/formatting via LSP, and CLI-backed Check/Build/Run commands
- `stdlib/` — manifest-owned SDK module tree: `process/`, `io/`, `memory/`, hidden `memory/managed/`, plus backend support under `stdlib/native/`
- `packages/` — higher-level ordinary Eido libraries built above stdlib
- `installer/` — SDK assembly/installation ownership
- `tests/integration/` — cross-component SDK/tool/library integration tests
- `examples/` — executable Eido examples
- `docs/` — architecture, testing, feature, and v0 specification documentation

## Flows
- compile: CLI/tool adapter -> compiler tooling API -> `EidoProject` + `CompilationOptions` -> per-source lexer/parser -> merged AST -> generic-class static specialization -> target-aware semantic analysis -> typed/resolved HIR -> policy-neutral `memory_metadata` phase -> selected Eido memory-policy phase binds generic semantic event points -> hidden Eido runtime methods -> Nim emitter -> Nim toolchain -> native executable (for executable targets)
- check: CLI/LSP/MCP/CI adapter -> compiler tooling API -> `EidoProject` -> parser + semantic analysis -> `ProjectCheckResult`; current fail-fast compiler yields at most one diagnostic per run, but the public result is sequence-shaped for future recovery
- feature acceptance: Eido source -> compiler pipeline -> generated Nim -> `nim e` -> assertion
- full test run: compile aggregate once with adaptive `--parallelBuild:N` -> compiler suites + individual feature tests -> isolated parallel processes via `execProcesses` -> bootstrap CLI integration -> Eido-written CLI dogfood integration

## Compiler-standard Eido compile-time route
- generic phase host -> `compile_time/host.nim` compiles compiler-owned Eido phase modules without recursively invoking standard phases -> parses their embedded `module.yaml`, preserves each source as its own `SourceUnit`, and therefore applies normal per-file module validation -> caches one build-machine executable per phase-module/native-bridge fingerprint -> invokes it with a private semantic snapshot -> returns protocol records; the phase/native bridge never enter stdlib or target binaries.
- semantic snapshot -> `compile_time/snapshot.nim` assigns invocation-local integer handles to semantic types/fields/callables/values and recursively discovers callable locals from structured HIR -> `compiler/compile_time/native/eido_native.nim` exposes read-only `Compiler`, `TypeInfo`, `FieldInfo`, `CallableInfo`, and `ValueInfo` contracts to compiler-owned Eido strategy code.
- private dynamic Storage layout -> `compile_time/target_storage_layout.nim` maps semantic type handles to the current backend Storage representation -> private `StorageInfo.sizeOf/alignmentOf` calls are available only inside compiler-owned phase source; ordinary Eido continues to use public `Storage<T>.size()/alignment()`.
- memory policy selection -> `pipeline/options.nim` defines `MemoryStrategy`/`CompilationOptions` -> CLI `--memory=gc|manual` chooses target runtime policy. `gc` runs the generic metadata phase plus private `memory_policy_gc`; `manual` currently rejects identity-bearing class representation/construction until explicit manual object semantics exist.
- metadata architecture -> `compiler/compile_time/phases/memory_metadata/MemoryMetadataBuilder.eido` computes target payload alignment/offsets plus identity-bearing field/value facts only -> private `MemoryMetadata.field/identityField/layout/identityValue` records carry invocation-local handles -> `compile_time/memory_metadata_phase.nim` resolves them to `CompileTimeMemoryMetadata`. No roots, trace plan, safepoints, retain/release, or allocator policy cross this compiler boundary.
- policy instrumentation -> compiler exposes generic semantic event kinds in `compile_time/instrumentation_model.nim` -> private Eido `memory_policy_gc/runner.eido` chooses only the events it needs and binds each to an ordinary hidden Eido method -> `compile_time/runtime_policy_phase.nim` transports those bindings -> `backend/nim/emitter/runtime_bindings.nim` resolves the selected methods by normal `MethodId`. Compiler code contains no GC handler names or implementation-class knowledge.
- construction/runtime route -> source `Class { ... }` remains semantic construction in compiler/HIR -> object runtime helpers validate/initialize fields and invariants -> storage acquisition crosses the generic construction event chosen by Eido policy -> runtime-backed class/interface identities currently lower to direct `int64` payload addresses -> generated Nim owns only representation glue (`eidoMemoryPresent/Get/PayloadAt`), not allocation policy.
- target memory route -> hidden `MemoryValueRegistry` stores live identity reports selected by the GC policy, `MemoryTypeRegistry` stores generic field/layout facts, `MemoryRuntime` contains ordinary handlers selected by the policy, and `ManagedGcRuntime` alone interprets those reports as mark/sweep roots/traversal over `ManagedHeapAllocator` + `Storage`. GC headers remain Eido-owned; a Storage-backed back-pointer immediately before each payload recovers the private header from the public runtime identity.
- runtime source attachment -> hidden policy sources carry `soCompilerRuntime`; hidden language services carry `soLanguageRuntime` plus a semantic capability such as `lrcString` or `lrcClassCopy` -> base analysis filters hidden origins -> target compilation selects only user-HIR-required language capabilities plus the active memory-policy runtime. Standalone/raw-source projects attach selected SDK sources without compiler knowledge of implementation class names.
- temporary-expression safety -> the compiler exposes generic temporary-scope and stable-statement event points. The current Eido GC policy binds them to handlers that defer collection while temporary depth is nonzero and evaluate collection pressure at stable boundaries; another policy may omit or interpret those event points differently.

## Storage substrate route
- generic storage -> `Storage<T>` materializes typed `allocate`, raw-to-typed block `view`, byte-offset `viewAt`, `slice`, `capacity`, `address`, `read`/`write`/`release`, and size/alignment queries; `Storage<Byte>` additionally provides raw allocation, external `fromAddress`, and explicit ownership recovery through `adoptAddress`. `eido_storage.nim` remains the single physical allocation substrate; higher memory policies use these APIs rather than defining native allocator/header structures.
- `Storage<T>.view`, `viewAt`, and `slice` are allocation-free borrowed capabilities. `view` reinterprets raw blocks, while `viewAt` targets a checked byte offset inside one raw block. `address` exposes the base address; `fromAddress` describes external memory without owning it, while `adoptAddress` explicitly reconstructs an owning raw descriptor for later `release`. Higher allocation strategies remain ordinary Eido policy above Storage.
- first Eido memory-policy layer -> `stdlib/memory/arena.eido` defines generic `Arena<T>` with one owning `Storage<T>` field and an Int cursor -> static `create(capacity)` obtains the single backing allocation -> instance `allocate(count)` returns a borrowed `Storage<T>.slice` and advances the cursor -> `remaining()` derives free slots -> `reset()` rewinds the cursor -> `release()` releases the root. Arena contains no `sizeof`, alignment, pointer arithmetic, or raw allocator mechanics.
- callable Storage-result provenance -> `semantic/analysis/storage_result_provenance.nim` infers one consistent owned/borrowed result category from ordinary Eido callable source -> `FunctionSymbol`/`MethodSymbol` carry that category -> `semantic/analysis/storage_value_provenance.nim` preserves it at caller bindings and persistent construction boundaries -> borrowed callable results remain non-releasable and cannot escape into owning Storage fields. Lifetime invalidation across Arena `reset`/`release` remains intentionally unverified until the future control-flow/borrow checker.
- contract-safe Storage observation -> `semantic/effects/native_observation.nim` recognizes compiler-owned `Storage.capacity`, `Storage<T>.size()`, and `Storage<T>.alignment()` as verified observational native behavior -> contract validation/effect inference allow layout/capacity queries without making allocation/write/release generally contract-safe.
- stdlib exposure -> source-free `stdlib/module.yaml` declares public `process`/`io`/`memory` children plus hidden `text`/`runtime` children and re-exports only public roots -> `stdlib/memory/module.yaml` owns `Memory<T>` + `Arena<T>`, hidden `memory/managed` owns GC policy runtime, hidden `text` owns String runtime, and hidden `runtime` owns detached-copy support -> `compiler/src/stdlib/builtin_sources.nim` recursively embeds/parses the same manifest tree and adds only umbrella `eido.stdlib` as the implicit user dependency.
- hosted/embedded split occurs below Storage: the same frontend/type/HIR semantics can target hosted allocation or fixed/static/pre-provisioned memory without changing Arena or higher Eido policies. Primitive raw-to-typed Storage and pure String operations have been smoke-tested under Nim `--mm:none`; graph-copy scratch is also Storage-owned. Strict every-path independence still waits on trap handling and remaining documented bootstrap/platform dependencies.
